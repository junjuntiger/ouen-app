# セキュリティ設計書

**プロジェクト名：** shinEDO-ouen（OUEN-APP）
**作成日：** 2026-06-25
**更新日：** 2026-08-17

## 1. 対策済み項目

### 1-1. 認証・認可

| 対策 | 内容 | 実装箇所 |
|---|---|---|
| メール＋パスワード認証 | Supabase Authによるメールアドレス・パスワード認証 | Supabase Auth |
| メールアドレス確認 | 新規登録時の確認メール送信（Supabase側の設定に依存、既定でON） | Supabase Auth |
| セッション管理 | Supabase SDKによる自動トークン発行・リフレッシュ | supabase-js内部処理 |
| RLSによる認可 | サーバーコードを介さず、Postgres側でリクエストごとに`auth.uid()`を検証 | Supabase RLS |

### 1-2. データアクセス制御

| 対策 | 内容 |
|---|---|
| Row Level Security | `profiles`・`transactions`ともにRLSを有効化、未認証アクセスは全拒否 |
| プロフィール書き込み制限 | 自分の行、または`is_admin=true`のユーザーのみ更新可 |
| 取引の直接書き込み禁止 | `transactions`へのINSERTポリシーを設けず、`create_ouen_transaction()`経由のみ許可 |
| OP残高の改ざん防止 | 取引作成時のOP加算はRPC（SECURITY DEFINER）内でのみ実行、クライアントから他人の`op`を直接updateすることは不可 |
| 自己申告額のみでのOP水増し防止 | `create_ouen_transaction()`は取引を`pending`（確認待ち）で作るだけでOPを加算しない。受け取る側が`confirm_ouen_transaction()`で確認（`to_user_id`本人のみ・`pending`時のみ実行可）して初めてOPが加算されるため、支払う側が支払額を過大申告するだけではOPを増やせない |
| 取引削除の制限 | 管理者（`is_admin=true`）のみ削除可能 |
| メールアドレスの非公開 | `profiles`にはemailを持たせず、管理者専用RPC `admin_list_users()`（`is_admin()`チェック付き）経由でのみ取得可能にし、一般ユーザーには非公開 |
| 写真アップロードの制限 | Storageの`avatars`バケットで、本人の`{uid}/`フォルダ以外への書き込みを拒否 |

### 1-3. 入力バリデーション

| 対策 | 内容 | 実施場所 |
|---|---|---|
| 必須項目チェック | 名前・メールアドレス・パスワード等の未入力を拒否 | フロントエンド |
| 金額バリデーション | 支払い金額が定価合計を下回る場合は送信不可 | フロントエンド |
| 画像形式・サイズ制限 | 画像ファイル以外、および5MB超のファイルを拒否 | フロントエンド |
| エラーメッセージの日本語化 | Supabaseから返る英語エラーを主要パターンに応じて翻訳して表示 | フロントエンド |

### 1-4. 通信セキュリティ

| 対策 | 内容 |
|---|---|
| HTTPS強制 | Vercel・Supabaseともにデフォルトですべての通信をHTTPS化 |
| APIキーの扱い | フロントエンドに埋め込むのはSupabaseの公開用（anon/publishable）キーのみ。書き込み権限はRLSで制御されるため、このキー自体が漏れても直接的な権限昇格にはならない |

## 2. 既知の課題・今後の検討事項

| 項目 | リスク | 対策案 |
|---|---|---|
| メール送信のレート制限 | Supabase組み込みSMTP（無料枠）は送信数が非常に少なく、大量登録時に「確認メールが送れない」状態になりうる | カスタムSMTP（Resend等）＋送信ドメイン認証の導入 |
| 自分の`op`列を直接更新できる余地 | `profiles_update_self_or_admin`ポリシーは行単位の許可であり、列単位の制限はない。UI上は`op`を編集する手段がなくても、Supabase APIを直接叩けば理論上は自分の`op`を書き換えられる | カラムレベルの制御（トリガーで`op`の変更を拒否し、管理者操作またはRPC経由のみ許可する等）の追加を検討 |
| 認証時のボット対策なし | メール＋パスワード認証にreCAPTCHA等の追加防御は導入していない | Supabase AuthのRate Limits設定の見直し、必要に応じてCAPTCHA導入 |
| プロフィール写真のモデレーション未実装 | 不適切な画像がアップロードされる可能性がある | 手動監視、または画像解析APIによる自動チェックの導入 |
| アカウント削除機能未実装 | 退会時のデータ削除手段がない | 削除フロー・関連データのカスケード削除の設計 |
| 取引削除がOPを連動して戻さない | 管理画面で取引を削除してもOP残高は自動修正されない | 削除時に該当分のOPを戻す処理の追加、または削除を禁止し取消フラグ方式に変更 |

## 3. 環境変数一覧

### フロントエンド用（`VITE_`プレフィックス、Viteが埋め込む）

| 変数名 | 説明 |
|---|---|
| VITE_SUPABASE_URL | SupabaseプロジェクトのURL |
| VITE_SUPABASE_ANON_KEY | Supabaseの公開用（anon/publishable）キー |

サーバーサイド専用の環境変数は存在しない（カスタムAPIサーバーを持たないため）。

---

## 4. .env テンプレート

```bash
VITE_SUPABASE_URL=https://xxxxxxxx.supabase.co
VITE_SUPABASE_ANON_KEY=sb_publishable_xxxxxxxxxxxxxxxxxxxx
```

## 5. .gitignore に含めるべきファイル

```
.env
node_modules/
dist/
```

> `.env`には接続情報のみで、いわゆるservice_role（管理者権限）キーは含めない。service_roleキーは絶対にフロントエンドや`.env`（クライアント公開用）に置かず、必要な場合はサーバー専用の環境でのみ扱うこと。
